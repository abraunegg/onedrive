This document describes the behaviours and scenarios covered by the OneDrive Client for Linux end-to-end (E2E) tests. The suite runs under GitHub Actions against dedicated Microsoft OneDrive accounts and performs real synchronisation operations. Test entries describe **the configuration or operation being exercised and the expected behaviour**, so readers can identify whether a specific use case is covered. The catalogue is not an exhaustive list of all possible Microsoft Graph responses or client configurations.

### Personal and Business Account Testing

Personal and Business end-to-end testing executes the complete standard suite against the **default drive** of each authenticated account, without setting an explicit `drive_id`. Microsoft Graph therefore resolves the primary Personal or Business drive, and the tests exercise discovery, enumeration, path traversal, metadata, upload, download, delete and reconciliation in that ordinary account-bound context. A separate Personal workflow checks the **15-character `driveId`** representation.

Personal and Business shared folders are covered in distinct suites. Shortcut-anchored content and directly shared files can use other remote drive identifiers, remote item identities and different path-resolution behaviour, so they cannot be treated simply as normal account-root directories.

### SharePoint Account Testing

SharePoint testing runs the **same complete standard test suite** but supplies an explicit `drive_id` in the client configuration. This deliberately targets a SharePoint-backed document library rather than the account's default OneDrive root. It validates the existing tests under a different Graph drive object, including library-specific discovery, enumeration, metadata, path traversal and upload/download/delete reconciliation. A PASS on the default Business drive alone does not establish these SharePoint drive-specific paths.

### Test results and recovery

Tests record the effective runtime options using `--display-running-config` and distinguish setup, the operation being tested, independent verification and cleanup. A green exit code alone does not prove that the intended behaviour occurred. Where remote renames/moves are tested, identity-preserving operations are distinguished from delete-and-recreate operations; client SQLite databases are examined only **after the owning process has stopped**.

A clean primary PASS is distinct from a failure recovered by a targeted debug rerun (**PASS WITH RECOVERY**). Mandatory cleanup and verification must also succeed for the workflow gate to pass. Scenario results remain attributable to their owning test cases.

### Contributing Additional Test Cases

Although this suite exercises a broad set of real filesystem and Microsoft Graph behaviours, it is **not exhaustive**. If you encounter a case that is not represented, or discover that a listed scenario does not actually exercise the described option or outcome, raise a discussion explaining the configuration, stimulus and expected result, or propose a test-harness pull request.

Where the objective is already covered, prefer adding a named scenario with explicit positive/negative controls and independent verification; create a new test case when the behaviour is genuinely distinct. The objective is to document and continuously improve **demonstrable coverage**, not merely increase the number of green tests.
